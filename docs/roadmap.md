## 四条贯穿全程的规矩

这三条是 Day 1-9 实测出来的，写在最前面因为每一步都要遵守。

### 1. 三层验证，每步都跑

```
pnpm typecheck   类型契约
pnpm test        行为（node --test 纯函数 + vitest 组件）
pnpm verify      真浏览器（能证明前两层证明不了的东西）
```

后端加入后追加 `pytest`。**每一步结束时三层必须全绿**，不接受"先欠着"。

### 2. 验收的裁判必须没参与被验收的改动

换实现时保持既有的断言和选择器不变，那样测试才是独立裁判。
同时换实现和改断言，全绿只证明"新代码和新断言自洽"。

### 3. 域名和地址永远是配置，不进代码

产品代码**完全不知道自己跑在哪个域名下**。所有地址从环境变量读，
由部署者（你、或私有部署的客户）填。见 `.env.example`。

这不是洁癖，是私有部署的硬性要求：客户会用他们自己的域名
（`https://kb.某公司内网.local`），我们不可能提前知道那是什么。
同一份代码要能跑在本地开发、演示服务器、客户内网三种环境下而一行不改。

会咬人的位置（现在知道就不会写死）：

| 配置项 | 写死的后果 |
|---|---|
| `VITE_API_URL` | 换域名前端全废 |
| `APP_URL` | 用户点邮件里的链接跳到别人的域名 |
| `CORS_ORIGINS` | 客户部署后浏览器全部拦下请求 |
| `COOKIE_DOMAIN` | 跨子域登录失效 |
| `LLM_BASE_URL` / `LLM_MODEL` | 换不了模型（大陆环境必须能换） |

**顺带的好处：整个阶段 A 到 C 都不需要碰域名。** 域名只在阶段 D 真正部署时才用到。

### 4. 新写的断言要先证明它会失败

写完就绿的断言不说明任何事。故意把被测代码改坏，确认它真的报错，再改回来。
这一步花两分钟，买到的是"这条断言是真裁判"。

**学**：服务端状态 vs 本地状态的区别、缓存、失效、重试、请求去重；TanStack Query。

## 阶段 B：后端与数据地基（约 25 天）

**这是整个项目最不能返工的阶段。** 建表和鉴权的决定错了，后面每一步都要跟着改。
`apps/api/README.md` 里的硬约束在动手前必须重读一遍。

### B1 · FastAPI 骨架

ASGI、配置管理、结构化日志、`/health`、OpenAPI、**API 版本前缀 `/api/v1`**、
CORS 白名单、统一异常响应。

**验收**：`/health` 和 OpenAPI 可用；输入错误返回稳定且前端可消费的错误结构。

### B2 · 数据模型与迁移 ★ 最关键的一步

PostgreSQL + SQLAlchemy 2.x + Alembic。

**建表前必须已确定的六条**（详见 `apps/api/README.md`）：

1. `resources` 通用表：`source_type` / `source_id` / `external_id`（组唯一，保证幂等）
   / `source_updated_at` / `acl_principals text[]` + GIN / `metadata JSONB`
2. **每张业务表带 `org_id`**，且它是复合索引的第一列
3. `audit_logs` append-only，含 `actor_type` + `on_behalf_of`
4. `deleted_at`（软删）+ `purged_at`（合规清除）两个字段
5. `acl_principals` 存带类型前缀的字符串（`user:123` / `group:eng`）
6. **向量维度定 1024**，`chunks` 表加 `embedding_model` + `embedding_dim` 两列
   （为将来换模型时新旧向量并存、灰度迁移留门）

表：`organizations` `users` `resources` `chunks` `conversations` `messages`
`citations` `ingestion_jobs` `audit_logs`

**验收**：从空库一键迁移和回滚；外键、唯一约束、常用查询索引完整。

### B3 · 认证与授权

密码哈希（argon2 或 bcrypt）、Access/Refresh Token、令牌轮换、
**鉴权双模式（Cookie + Bearer）**、RBAC、资源归属校验。

**测试要覆盖**：错误密码、过期令牌、刷新令牌复用、跨用户访问、**跨组织访问**、
两种凭据方式各自走通。

**★ 本地 HTTP 与生产 HTTPS 在 Cookie 上有真实的行为差异**，不是配置差异：

| Cookie 属性 | 本地 `http://localhost` | 生产 `https://` |
|---|---|---|
| `Secure` | 加了浏览器就**不发送** | 必须加 |
| `SameSite=None` | 要求同时有 `Secure`，所以本地用不了 | 跨站场景必须 |
| `Domain=.example.com` | localhost 上无意义 | 跨子域共享登录态要用 |

后果是经典的**"本地登录正常，上线后登不进去"**——而排查方向会往鉴权逻辑上走，
实际问题在 Cookie 属性。

**处理办法：本地也用 HTTPS。** `mkcert` 给 localhost 签一张本地信任的证书，
两条命令。这样本地和生产的 Cookie 行为一致，那类 bug 根本不会出现。

对比另一种办法（把 Cookie 属性做成配置 `COOKIE_SECURE=false`）：它更简单，
但代价是**本地永远测不到生产走的那条路径**。

选 mkcert 的理由和「用真浏览器验证而不只靠 jsdom」是同一条：
**让测试环境接近真实环境，而不是让代码去适应测试环境的简化。**

**验收**：前后端真实登录打通；用户 A 读不到 B 的资源；组织 X 读不到 Y 的；
**本地在 HTTPS 下登录流程走通**（证明 Cookie 属性和生产一致）。

### B4 · 业务 API 与上传

资源、对话、消息 CRUD、分页、上传校验（MIME + 大小）、
**断点续传的接口形状**（可查询已上传偏移、可从偏移继续）。

上传接口只负责校验、存储、创建处理任务——不做解析。

**验收**：接口有明确状态码；分页稳定；非法文件、超限文件、重复请求处理正确。

### B5 · 后端测试与阶段验收

pytest fixture、依赖覆盖、事务隔离、种子数据。

**阶段 B 出口标准**：
- 后端测试可重复运行（不依赖执行顺序）
- 前后端核心 CRUD 全部打通，mock 后端可以下线
- 迁移能在全新环境完成
- 权限隔离测试覆盖跨用户 + 跨组织 + 两种凭据方式

| C4 | 混合检索：向量 + 全文、RRF 融合、**org + ACL 双层过滤** |
| C5 | 流式生成、引用对齐、拒答、上下文预算、Provider 错误映射、提示注入基础防线 |
| C6 | 评估：30-50 条黄金数据集，离线报告与基线 |
| C7 | 只做一个经评估证明有效的优化（Query Rewrite / Reranker / 缓存三选一） |

### 阶段 C 的 Provider 约束：任何一家都能接

**支持范围**：OpenAI、Anthropic（Claude）、国产模型（DeepSeek / 通义 / 智谱 / Kimi）、
**自建或第三方中转站**、客户内网自部署（vLLM / Ollama）。

配置形状见 `.env.example`，设计理由与差异清单见 `apps/api/README.md` 的
「Provider 抽象」一节。这里只列**必须在本阶段兑现的三件事**。

**一、协议类型和厂商解耦。**

不能只有 `base_url`，还要 `LLM_PROVIDER` 指明协议：

| 类型 | 端点 | 认证 |
|---|---|---|
| `openai-compatible` | `POST {base}/chat/completions` | `Authorization: Bearer` |
| `anthropic` | `POST {base}/messages` | `x-api-key` + `anthropic-version` |

Claude 官方 API 需要**第二个适配器**，"换个 base_url"不成立。
但中转站若把 Claude 包成 OpenAI 兼容格式（多数如此），用第一种类型即可。

**二、六处差异要在适配器层抹平**：向量维度、流式格式、错误映射（归到 `ApiError`
五种 kind）、上下文窗口、token 计数字段、工具调用格式。

**三、★ 向量维度是唯一影响 schema 的，B2 建表时就要定。**

pgvector 的 `vector(N)` 在建表时写死。OpenAI 1536/3072、通义与 BGE-M3 都是 1024。
**换 embedding 模型 = 改列定义 + 重算所有历史向量**（十万 chunk 要跑几小时并重付一次费用）。

推荐 **1024**：通义和 BGE-M3 都是这个值，而中文检索效果又优于 OpenAI 的 embedding。
启动时必须校验配置与列维度相等，不一致就拒绝启动。

**Embedding 走 API，不本地跑模型**——本地跑 BGE-M3 要 1-2GB 常驻，部署机只有 2GB。

**四、中转站的数据风险要在产品里显式标注。**

中转站会看到全部 prompt，也就是知识库原文——而那往往是全公司最敏感的资料。

| 场景 | 推荐 | 风险 |
|---|---|---|
| 开发 / 演示 | 中转站 | 可接受 |
| 企业生产 | 直连官方 API | 数据到模型厂商 |
| 高敏感 / 合规 | 客户内网自部署 | 数据不出内网 |

不能让管理员以为所有 Provider 都等价。这是「治理」的一部分，
和智能体权限继承、审计日志属于同一根支柱。

**阶段 C 出口标准**：
- 20 个问题 Recall@5 ≥ 85%
- **跨用户与跨组织检索零泄漏**（红队测试，不是抽查）
- 每个事实型回答附可点击来源；无证据时明确拒答
- 前端取消会真的终止后端生成
- 同一文档重复处理不产生重复 chunk
- 报告含 Recall@k、引用正确性、回答忠实度、P50/P95 延迟、单次成本
- **至少接通两家 Provider 且能靠改配置切换**（建议 DeepSeek + 一家 OpenAI 兼容中转，
  验证适配器层真的抹平了差异——只接一家等于没有抽象）
- 启动时校验 `EMBEDDING_DIM` 与数据库列维度一致，不一致拒绝启动

**这是 MVP 的完成点。** 到这里可以给真人用了。

## 阶段 D：部署与工程化（约 20 天）

**刻意排在代码感知之前**：没上线过的系统不知道自己哪里会坏。

| 步骤 | 内容 |
|---|---|
| D1 | 容器化：多阶段构建、非 root、健康检查、Compose 起全套依赖 |
| D2 | Linux 部署：Nginx/Caddy、域名、HTTPS、持久化卷、迁移与备份 |

### 交付形态：域名是客户的事，不是产品的事

企业交付的真实形态：

```
你交付的                     客户提供的
─────────────────────       ─────────────────────
Docker Compose 文件          服务器
镜像                         域名
.env.example                 证书（或让 Caddy 自动签）
部署文档                     填好的 .env
```

客户的 IT 部门拿到交付物，填几个环境变量，`docker compose up`。
**域名从头到尾不经过开发者的手。**

所以本地开发只用 `localhost` 是正确的，不是妥协。而真正要验证的不是域名，
是**"别人能不能部署"**——这件事完全可以在本地验证，不需要任何域名：

```bash
cp .env.example .env
# 填成和开发时不同的值，证明代码没依赖某台特定机器的环境
docker compose up
# 从另一个端口 / 主机名访问，确认没有写死的地址
```

这就是下面出口标准里「一条命令在全新环境启动系统」的实际含义。
它验的是**代码里没有只在开发者机器上成立的假设**。

### 求职 demo：三个选项，A 就够用

产品设计不需要域名，但简历上放一个能点开的链接需要。
而大陆服务器放公开 demo 就得备案——这是唯一真的绕不过的地方。

| 选项 | 做法 | 判断 |
|---|---|---|
| **A** | 不做 live demo。README 三张截图 + 3-5 分钟演示视频 | **对求职完全够用**。很多人根本不点 demo 链接，而一个打不开的 demo 比没有 demo 更糟 |
| B | demo 放境外小机器（Hetzner €4/月），不用备案 | 想要 live demo 时的最省路径。大陆服务器留着开发和内部测试 |
| C | 老老实实备案 | 一次性、免费、一两周。做过备案本身是国内做产品的必要经验 |

**建议 A，以后有需要再补 B。** 截图和视频本来就是本阶段出口标准要求的，
性价比最高。备案和域名都是"用的时候再办"的事。

### 阶段 D 的三条环境约束（大陆服务器，2 核 2GB）

**一、ICP 备案要提前一个月启动，它会卡住整个上线验收。**

大陆服务器绑域名必须备案，不备案的后果是**云服务商直接封掉 80/443**。

```
域名实名认证    1-2 天
提交 ICP 备案   通过云服务商后台，免费
工信部审核      1-3 周（各省不同）
公安备案        备案通过后 30 天内补办
```

**域名要买 `.com` 或 `.cn`**——工信部可备案顶级域名白名单里**没有 `.dev` 和 `.app`**。
从服务器同一家云厂商买，备案流程和域名管理是打通的。

个人备案不允许"商业性质"内容：带定价页和"立即购买"的产品官网可能被驳回，
演示项目通常没问题。

**二、2GB 内存能跑全栈，但要精细安排。**

估算：OS 200-300MB + Postgres 300-500MB + Redis 30-50MB + FastAPI 200-300MB
+ Worker 200-400MB + Next.js 150-250MB + Caddy 20MB ≈ **1.1-1.8GB**。
能塞进去，没有余量。五条必做：

1. **镜像在 CI 构建，绝不在服务器上构建**——`next build` 单独就要 2GB+，会 OOM
2. **加 2-4GB swap**——不是当内存用，是防 OOM killer 突然杀掉 Postgres
3. **Embedding 走 API**，不本地跑模型
4. **Worker 并发限制为 1**——两个 Worker 同时解析大 PDF 会把内存打穿
5. **Postgres 调参**：`shared_buffers=256MB`、`work_mem` 调小、`max_connections≈20`

**三、公开 demo 会被刷，而每次提问都是真金白银。**

一个开放的 RAG demo，任何人都能写脚本循环请求。必须做：

- 演示账号硬限流（每小时 20 次提问）
- demo 环境用最便宜的模型

| E6 | 调用图（近似，必须标注置信度） |

| E8 | **变更归因**：串联代码 + PR 讨论 + 设计文档 + 事故复盘 |

顺序和原来不同：**依赖图和图的 diff 提到调用图之前。**
理由见下面第三条——前者可靠且工程量小，后者必然近似。

### 图的四条设计决定（2026-07-30 定，做的时候容易图省事忽略）

#### 一、一张图回答一个问题，不做"全貌图"

一个真实的中等项目有 300 个文件、2000 条 import 边。全画出来是一团毛线球，
**比不画更糟**——它给人"我看到了全貌"的错觉，实际什么信息都没传递。
市面上大部分"自动生成架构图"的工具就死在这里。

| 坏的请求 | 好的请求 |
|---|---|
| "给我看架构图" | "billing 模块依赖了什么？" |
| "画出所有调用关系" | "改 `calculate_discount` 会波及哪些模块？" |
| "系统全貌" | "`POST /orders` 这个请求走过哪些层？" |

右边三个都有明确的**起点和边界**，所以图小、可读、能验证。

这决定了功能形态：**不是一个"架构图"页面，而是从当前位置出发的一次追问。**
正好和 VS Code 插件的场景吻合——你在看某个文件，问的一定是关于它的问题。

#### 二、★ 边必须标注置信度，否则违背自己的溯源原则

产品承诺是"每条边可追溯"。但不同来源的边可靠程度差别很大：

| 边的来源 | 确定性 |
|---|---|
| `import` / `require` 语句 | **确定**（静态可解析，指到具体那一行） |
| 直接函数调用 `foo()` | **确定** |
| 方法调用 `obj.method()` | **推断**（动态语言里 `obj` 的类型要靠推断） |
| 反射 / 装饰器 / 依赖注入 | **可能漏**（`getattr(mod, name)()` 静态看不见） |
| 事件 / 消息队列 | **看不见**（发布方和订阅方在代码里没有直接联系） |

所以视觉上必须区分：

```
A ──────► B     实线 = 静态确定
C ┄┄┄┄┄► D     虚线 = 类型推断得出
E ╌╌?╌╌► F     问号 = 可能存在但无法确认
```

**不做这个区分，就是把一条猜出来的边画成实线——和让 LLM 编一个答案是同一类错误，
只是形式不同。** 而做了区分反而加分：诚实地说"这里我不确定，你自己看一眼"
比假装全知更可信。

这条属于"当时不写下来，做的时候就会图省事画成实线"的东西，所以单独记。

#### 三、先做依赖图，调用图后做

依赖图（import 层面）能做到几乎全对。调用图在动态语言里**必然近似**——
Python 的鸭子类型、装饰器、动态导入让静态分析注定有漏。

依赖图可靠、有用、工程量小得多，先做它。

#### 四、图的 diff 是优先级最高的形态

比静态架构图有用得多：

```
这个 PR 让架构发生了什么变化？

+ billing/calculator.py  →  external/tax_api.py   【新增依赖】
- billing/invoice.py     →  utils/legacy_fmt.py   【移除依赖】

⚠️ 新增了一条从 billing 到 external 的依赖。
   这个方向此前不存在——billing 一直是不出网的。
```

四个理由：

1. **它出现在有人做决定的时刻。** 代码审查时人本来就在判断"这个改动可以吗"，
   而"新增了一条跨层依赖"是审查者很难靠读 diff 发现的——它藏在一行 import 里。
2. **它是被动触达的。** 自动贴到 PR 评论，不需要谁记得打开工具。
3. **架构腐化是渐进的。** 没人会一次性把架构搞坏，都是每个 PR 加一条"就这一次"，
   两年后没人认得出原来的设计。图的 diff 是唯一能在每次改动时看见这个过程的东西。
4. **技术上比全量图简单。** 只需算两个 commit 的依赖图做差集，
   不用解决"如何布局 2000 条边"这个难题。

### 技术选型方向（真做时再定）

**解析：tree-sitter。** 一套 API 支持几十种语言、增量解析、容错
（语法错误的文件也能部分解析）。GitHub 自己的代码导航就是用它。
比给每种语言接一个专用解析器现实得多。

**渲染分两条路，第一条先做**：

| 场景 | 方案 | 理由 |
|---|---|---|
| PR 评论 / 文档嵌入 | **Mermaid** | GitHub 原生渲染 Mermaid 代码块，**零成本嵌入**，不需要图片服务器 |
| 交互式查看 | 自渲染 SVG + `elkjs` 布局 | "点节点打开文件"需要真交互，Mermaid 给不了 |

第一条成本低、见效快，而且 PR 场景正是上面那个优先级最高的形态。

**阶段 E 出口标准**：
- 对一个真实的中等规模仓库，"这段代码为什么这样"能给出跨源引用
- 依赖图每条边都可追溯到具体的 import 那一行
- **推断出来的边在视觉上和确定的边不同**（这一条要有测试守）
- 图的 diff 能自动贴到 PR 评论
- 影响面分析的召回率有可测数字
- **没有一条边是 LLM 猜的**
