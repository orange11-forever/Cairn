## 三条贯穿全程的规矩

这三条是 Day 1-9 实测出来的，写在最前面因为每一步都要遵守。

### 1. 三层验证，每步都跑

```
pnpm typecheck   类型契约
pnpm test        行为（node --test 纯函数 + vitest 组件）
pnpm verify      真浏览器（能证明前两层证明不了的东西）
```

后端加入后追加 `pytest`。**每一步结束时三层必须全绿**，不接受"先欠着"。

### 2. 验收的裁判必须没参与被验收的改动

换实现时保持既有的断言和选择器不变，那样测试才是独立裁判。
同时换实现和改断言，全绿只证明"新代码和新断言自洽"。

### 3. 新写的断言要先证明它会失败

写完就绿的断言不说明任何事。故意把被测代码改坏，确认它真的报错，再改回来。
这一步花两分钟，买到的是"这条断言是真裁判"。

## 阶段 A：Web 客户端地基

> 状态：**A1-A9 已完成**（原 Day 1-9）。当前在 A10。

已完成：HTML/CSS 结构与响应式 → JS 交互 → 异步与错误状态 →
TypeScript 迁移 → Zod 校验层 → React 组件化 → Hooks 与受控表单。

现有资产：33 个源文件约 3100 行，108 个测试，七组浏览器场景验证。

### A10 · 服务端状态与 React 阶段验收

**学**：服务端状态 vs 本地状态的区别、缓存、失效、重试、请求去重；TanStack Query。

开头要先补讲两件 A9 问答暴露的薄弱点：
- `setState` 的机制（React 主动撤销不符合 state 的 DOM 值）与代价（每次都是一次重渲染）
- 什么值不该进 state（能算出来的、不影响渲染的）

**做**：
- 引入 TanStack Query，替换 `useAsyncAction` 在文档列表上的角色
- 文档查询、上传 mutation、删除、成功后自动失效并重新拉取
- 保留 `useAsyncAction` 用于登录（它不是服务端状态，是一次性动作）

**验收**：
- 上传成功后列表自动更新，不用手动刷新
- 同一份数据被两个组件用时只发一次请求
- 能解释一次状态更新为什么触发重渲染
- 三层验证全绿

**为什么不早点引入**：`useAsyncAction` 刻意做得薄，好让这一步能看清
手写服务端状态缺了什么——缓存、失效、重试、去重。先手写一遍再换库，
才知道库替你做了什么。

### A11 · Next.js App Router

**学**：文件路由、Layout、Server/Client Component 边界、环境变量、静态与动态渲染。

**做**：把原型迁成正式 Next.js 前端，路由拆成 `/login` `/documents` `/conversations`。

**验收**：直接访问和刷新任一路由都正常；能解释 Server 和 Client Component 的边界。

**顺带做**：把 `Sidebar` 改名（它渲染的是横向顶栏，名字从 A8 起就和现实不符）。

### A12 · 前端工程结构与数据契约

**做**：统一请求层、Zod 响应校验、Toast、错误边界、Skeleton、空状态。

**要在这一步收口的旧账**：
- `AssistantPanel` 显示 `error.message`，文档列表走 `describeStatus` 统一映射——
  两条错误文案路径不一致（A9 写测试时发现，记在 specs 里）
- `describeStatus` 在 `documents` 为空且 `dropped > 0` 时显示"还没有文档"，
  而真相是前端一条都没看懂

**验收**：页面不直接散落 fetch 调用；所有请求走统一错误处理。

### A13 · 鉴权前端

**做**：注册、登录、退出、会话恢复、受保护路由、401 自动处理（暂接 mock）。

**★ 这一步的决定不能只考虑 Web**：Cookie 是 Web 的最佳选择，但原生客户端要
Bearer + Keychain。设计时就要让两种方式并存。见 `apps/api/README.md` 跨平台约束第 1 条。

**验收**：未登录进不了工作台；令牌不在 `localStorage`；
能解释为什么 Web 用 HttpOnly Cookie 而原生用 Bearer。

### A14 · 流式聊天与引用 UI

**做**：mock SSE 实现逐字输出、停止生成、重新生成、引用跳转、失败重试。

**验收**：中途取消后请求确实终止；流式内容不造成布局跳动或消息重复。

### A15 · 前端测试与阶段验收

**做**：补齐登录、上传、问答三条关键路径；Playwright 写一条完整主流程 E2E。

**阶段 A 出口标准**：
- lint、typecheck、单元测试、E2E 全绿
- 移动端能完成核心流程（375px 宽无横向溢出，键盘可达）
- 能从空目录按 README 启动项目

## 阶段 B：后端与数据地基（约 25 天）

**这是整个项目最不能返工的阶段。** 建表和鉴权的决定错了，后面每一步都要跟着改。
`apps/api/README.md` 里的硬约束在动手前必须重读一遍。

### B1 · FastAPI 骨架

ASGI、配置管理、结构化日志、`/health`、OpenAPI、**API 版本前缀 `/api/v1`**、
CORS 白名单、统一异常响应。

**验收**：`/health` 和 OpenAPI 可用；输入错误返回稳定且前端可消费的错误结构。

### B2 · 数据模型与迁移 ★ 最关键的一步

PostgreSQL + SQLAlchemy 2.x + Alembic。

**建表前必须已确定的五条**（详见 `apps/api/README.md`）：

1. `resources` 通用表：`source_type` / `source_id` / `external_id`（组唯一，保证幂等）
   / `source_updated_at` / `acl_principals text[]` + GIN / `metadata JSONB`
2. **每张业务表带 `org_id`**，且它是复合索引的第一列
3. `audit_logs` append-only，含 `actor_type` + `on_behalf_of`
4. `deleted_at`（软删）+ `purged_at`（合规清除）两个字段
5. `acl_principals` 存带类型前缀的字符串（`user:123` / `group:eng`）

表：`organizations` `users` `resources` `conversations` `messages`
`citations` `ingestion_jobs` `audit_logs`

**验收**：从空库一键迁移和回滚；外键、唯一约束、常用查询索引完整。

### B3 · 认证与授权

密码哈希（argon2 或 bcrypt）、Access/Refresh Token、令牌轮换、
**鉴权双模式（Cookie + Bearer）**、RBAC、资源归属校验。

**测试要覆盖**：错误密码、过期令牌、刷新令牌复用、跨用户访问、**跨组织访问**、
两种凭据方式各自走通。

**验收**：前后端真实登录打通；用户 A 读不到 B 的资源；组织 X 读不到 Y 的。

### B4 · 业务 API 与上传

资源、对话、消息 CRUD、分页、上传校验（MIME + 大小）、
**断点续传的接口形状**（可查询已上传偏移、可从偏移继续）。

上传接口只负责校验、存储、创建处理任务——不做解析。

**验收**：接口有明确状态码；分页稳定；非法文件、超限文件、重复请求处理正确。

### B5 · 后端测试与阶段验收

pytest fixture、依赖覆盖、事务隔离、种子数据。

**阶段 B 出口标准**：
- 后端测试可重复运行（不依赖执行顺序）
- 前后端核心 CRUD 全部打通，mock 后端可以下线
- 迁移能在全新环境完成
- 权限隔离测试覆盖跨用户 + 跨组织 + 两种凭据方式

## 阶段 C：RAG 垂直链路（约 30 天）

到这一阶段结束，产品第一次成为**可用的东西**。

| 步骤 | 内容 |
|---|---|
| C1 | 对象存储、解析器接口、任务状态机 `pending/running/succeeded/failed` |
| C2 | PDF/Markdown/TXT/DOCX 解析、结构化切分、Embedding、pgvector 入库 |
| C3 | Redis 队列 + Worker：重试、指数退避、幂等键、超时、取消、死信 |
| C4 | 混合检索：向量 + 全文、RRF 融合、**org + ACL 双层过滤** |
| C5 | 流式生成、引用对齐、拒答、上下文预算、Provider 错误映射、提示注入基础防线 |
| C6 | 评估：30-50 条黄金数据集，离线报告与基线 |
| C7 | 只做一个经评估证明有效的优化（Query Rewrite / Reranker / 缓存三选一） |

**阶段 C 出口标准**：
- 20 个问题 Recall@5 ≥ 85%
- **跨用户与跨组织检索零泄漏**（红队测试，不是抽查）
- 每个事实型回答附可点击来源；无证据时明确拒答
- 前端取消会真的终止后端生成
- 同一文档重复处理不产生重复 chunk
- 报告含 Recall@k、引用正确性、回答忠实度、P50/P95 延迟、单次成本

**这是 MVP 的完成点。** 到这里可以给真人用了。

## 阶段 D：部署与工程化（约 20 天）

**刻意排在代码感知之前**：没上线过的系统不知道自己哪里会坏。

| 步骤 | 内容 |
|---|---|
| D1 | 容器化：多阶段构建、非 root、健康检查、Compose 起全套依赖 |
| D2 | Linux 部署：Nginx/Caddy、域名、HTTPS、持久化卷、迁移与备份 |
| D3 | CI/CD：GitHub Actions 跑前后端检查，主分支通过才部署 |
| D4 | 可观测性：Request ID、关键耗时、token 用量、错误日志、限流与配额 |
| D5 | 安全与性能：OWASP 检查、上传白名单、超时、轻量压测、上线检查清单 |

**阶段 D 出口标准**：
- 一条命令在全新环境启动系统；密钥不进镜像和 Git
- 公网 HTTPS 可访问；重启服务器后自动恢复
- **完成一次数据库备份和恢复演练**（备份成功 ≠ 能恢复）
- 故意提交一个失败测试会阻断流水线
- 能从一次失败请求定位到检索和模型调用
- 日志不含令牌、密码、完整私有文档
- 记录 P50/P95 延迟和并发能力

## 阶段 G：多端客户端（约 50 天）

前置：阶段 B（鉴权双模式）+ 阶段 D（稳定的线上 API）。

```
G1  PWA              manifest + Service Worker，可安装、能离线打开
    ↓ 收集真实使用数据，再决定要不要投原生
G2  VS Code 插件  ★  程序员向最高价值，技术上最简单（就是个 API 客户端）
G3  Tauri 桌面端     可直接复用 Next.js 前端
G4  IM 机器人        飞书 / Slack
G5  React Native     投入最大，放最后
```

**先 PWA 的理由**：企业内部工具的真相是员工多数在电脑前工作，
手机端使用率可能低到不值得做原生。用零成本的一步收数据，比直接投三个月更稳。
