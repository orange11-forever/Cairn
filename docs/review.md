# 代码审查规范

## 目标与门禁

按用户2026-10-13确认，采用满足当前需求的最小实现，验证和审查仅服务于本次改动的具体风险。默认实现者自查，只运行相关验证，不固定安排多轮审查。仓库仍采用零审批 Pull Request；现有CI门禁见[持续集成设计](ci.md)。本地不因CI要求而扩大检查，完整 `pnpm verify` 只在用户明确要求时运行。

## 实现原则

- 沿用已有直接实现，只解决当前需求；不为假设的未来场景添加兜底、重试、兼容层或抽象。
- 只在外部边界对实际输入和输出做必要校验，例如用户请求、第三方响应和持久化读写；内部代码信任已校验的契约，不逐层重复校验。保留当前业务所需的授权与数据完整性约束。
- 无法恢复的错误明确返回失败并提供定位信息，不吞错、伪装成功或隐式降级；没有实际恢复场景就不增加恢复机制。

## 按风险选择流程

- 小型、可逆改动：必要自查即可；不为简单文案、样式或机械修改新增测试、独立审查代理或流程文件。
- 一般功能：默认直接实现、阅读自身差异、运行一次相关验证；不自动派发实现或审查代理，也不默认创建独立规格、计划和审查报告。
- 实质改变迁移、数据保留、权限决策、并发正确性等边界时，先明确具体风险，再补对应证据；必要时增加一次同时检查需求与质量的独立审查。不能仅因文件或功能涉及这些名称就自动扩大流程。

测试证据绑定代码或制品，相同代码的最新通过结果直接复用。修复只补测修改的行为及直接影响；只有实际新失败、明确的关联风险或用户要求才扩大范围，不为收尾或换审查者重复运行。浏览器只检查变化的流程和布局，修正后确认对应问题；界面修改不重启未变化的后端验证。

没有固定的“规格审查→独立质量审查”双轮要求。需要审查时集中给出实质问题；修复后只确认对应差异和证据，不重新审整包。只有未解决的具体重大风险或用户明确要求，才增加审查轮次。

## 受影响边界

审查者必须同时阅读改动和它触及的边界，包括调用者、下游消费者、中间件顺序、框架默认行为、公开契约及生成制品。不能因为文件未出现在 diff 中就排除边界检查。

针对实际修改的外部边界，从以下路径选择相关验证，不为未触及的路径补齐测试矩阵：

- 正常成功；
- 输入与请求验证失败；
- 认证或授权失败；
- 数据库、网络或其他基础设施失败；
- 未预期异常。

无需逐项解释与改动无关的路径，也不为已经在外部边界校验的数据新增内部重复检查。

## API 契约检查

对发生变化的 HTTP/API 边界，只核对本次改动涉及或直接影响的维度：

- 状态码与方法语义；
- 成功和错误响应体 schema；
- `X-Request-ID` 与响应 `traceId` 的关联；
- CORS、安全头以及 `Allow`、`Retry-After` 等协议头；
- OpenAPI 声明和生成 SDK 是否与运行时一致。

测试必须在消费者可观察的边界断言行为。只断言源码包含某行、只覆盖成功路径，或只确认某个状态码存在，都不足以关闭相关风险。

## 审查输出

只记录实质问题、相关验证结果和未解决限制；普通任务直接写在交付说明中，不另建审查报告。结论必须对应当前代码；已经验证且未变化的证据可以复用，不能把未完成的检查写成通过。
