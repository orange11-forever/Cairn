## 一句话定位

**工程组织的知识层与智能体平台。**

不是"更强的飞书"。是**架在组织已有工作场所之上的智能层**——代码是一等公民，
每个答案可追溯到出处，AI 智能体受治理。

### 为什么不做飞书那种平台

聊天、语音会议、日历、在线文档编辑：**明确不做。** 三个理由：

1. **已商品化。** 每家公司都有飞书/Slack/Teams。做一个"更好的聊天"，
   用户的迁移成本是整个组织的沟通历史——没人会为了搜索更好而换掉 IM。
2. **难一个数量级。** 实时消息要处理在线状态、离线同步、消息顺序、已读回执、
   移动端推送与省电、多端一致性。这是几年和一个团队，不是"多写几万行"。
3. **做完不构成差异。** 差异在检索、溯源和代码理解，不在气泡框。

**正确动作是反过来：成为它们之上的一层。**

```
飞书 / Slack / 企业微信 / GitHub / Jira      ← 用户不换工具
        ↓ 作为数据源（连接器）
        ↓ 作为交付界面（机器人）
     Cairn                              ← 智能层
```

在飞书群里 @ 机器人问"计费逻辑改过几次、为什么"，得到一段带引用的答案——
**用户不需要改变任何习惯。** 这比"请大家搬到我的平台"好一个量级。

## 三根支柱

### 支柱一：可追溯的问答（已在建，Day 1-9 是它的前端）

核心约束一句话：**回答只依据已处理完成的资料，每个事实型回答必须附可点击的原文出处；
找不到依据时明确拒答，不编。**

这不是功能列表里的一项，它决定数据模型——引用的校验比答案文本本身更严，
因为一条指向不存在文档的引用比没有引用更坏：它让用户以为答案有依据。

### 支柱二：代码感知（新增，这是差异化的来源）

把要解决的问题精确成一句话：

> **"这段代码为什么是这样的？"**

现在没有工具能回答。答案散落在五处：代码注释、当初那个 PR 的讨论、一份设计文档、
一次事故复盘、某个群里的对话。新人要三个月才能串起来，而串起来的方式是去问那个待了五年的人。

**这个问题恰好需要支柱一的全部能力**（跨源检索 + 权限感知 + 引用溯源），
而它是飞书和 Glean 结构上都做不好的：
- 飞书的模型是"文档 + 沟通"，代码对它是纯文本附件
- Glean 有连接器，但把代码当文本切分——切在函数中间、丢掉调用关系、
  不认识 `getUserById` 在别处被引用

代码有文档没有的结构：**AST、调用图、git 历史、PR 与 issue 的关联、符号级引用。**
吃进这些结构是通用 RAG 做不到的护城河。

#### 图必须从真实代码推导，不能让 LLM 画

直接让 LLM 画架构图，它会**自信地错**——画出看起来合理但和真实调用关系不符的图，
而读图的人无法发现。这违背支柱一的承诺，且比文字错得更隐蔽（图更容易让人相信）。

| 真实来源 | 产出 | LLM 的角色 |
|---|---|---|
| import / 依赖关系 | 边 | 无 |
| 调用图（AST 解析） | 边 | 无 |
| 目录与模块结构 | 分组 | 给分组起人话名字 |
| git 历史 / 变更聚集 | 热点标注 | 总结"这块最近为什么频繁改" |

每个节点可点开看到那个文件，每条边可追到那一行 import。**图是可验证的。**

而且真实项目里最有价值的图不是漂亮的架构图，是**"改这个函数会影响到哪"**——
那必须从真实调用图算，LLM 猜不出来。

### 支柱三：智能体治理（新增，最可能有人付钱的一根）

企业的真实困境：员工都在用 AI，公司完全不知道谁用它做了什么。

| 问题 | 现状 |
|---|---|
| 谁能创建智能体 | 无人管 |
| 某个智能体能读哪些数据 | 不清楚，通常"它能读的全都能读" |
| 它上周替谁做了什么 | 查不到 |
| 这个月烧了多少 token、哪个部门 | 不知道 |
| 有人在文档里埋了提示注入 | 没有防线 |

**地基已经对上了：**

```
组织级租户 + ACL principals  → 智能体只能读它"代表的那个人"能读的东西
审计日志（append-only）      → 智能体做过什么有据可查
引用溯源                     → 智能体的输出可以被核对
不可信文档处理               → 提示注入的防线
```

**最关键一条：智能体必须以用户身份行动，继承那个人的权限。**
否则它是一个越权通道——实习生的智能体读到了 CEO 的文档。

这根支柱卖的不是"AI 能力"（那是商品），是**治理**。
治理是企业采购里预算最容易批的一类，因为不做过不了安全评审。

## 成品的样貌

### 用户看到的界面（多端）

| 界面 | 定位 | 技术 |
|---|---|---|
| **Web 工作台** | 主界面。搜索、问答、文档管理、智能体管理、图谱浏览 | Next.js |
| **桌面端** | 常驻工具，全局快捷键唤起搜索 | Tauri（复用 Next.js 前端，产物几 MB） |
| **手机端** | 以「读和问」为主，不做创作 | React Native + Expo |
| **IDE 插件** | ★ 程序员真正待的地方：选中代码直接问"为什么这样" | VS Code 扩展 |
| **IM 机器人** | 不改变用户习惯的交付面 | 飞书 / Slack 机器人 |
| **CLI** | CI 里跑影响面分析、把架构图产出到 PR 评论 | 命令行 |

**IDE 插件是程序员向的关键界面。** "这段代码为什么是这样"最自然的提问时机是
**正在看这段代码的时候**——选中一段，右键提问，得到来自 PR 讨论、设计文档、
事故复盘的带引用答案。它只是同一套 API 的另一个客户端。

### 系统内部

```
                     ┌─────────── 客户端 ───────────┐
   Web · 桌面 · 手机 · IDE 插件 · IM 机器人 · CLI
                     └──────────┬──────────────────┘
                                │  REST API（OpenAPI，带版本前缀）
                                │  鉴权双模式：Cookie（Web）/ Bearer（原生）
                     ┌──────────▼──────────┐
                     │      FastAPI        │
                     │  权限感知的检索与问答  │
                     │  智能体运行时与治理    │
                     └──┬───────────────┬──┘
                        │               │
          ┌─────────────▼──┐      ┌────▼─────┐
          │ PostgreSQL     │      │  Redis   │
          │ + pgvector     │      │  队列    │
          │ 资源·ACL·审计   │      └────┬─────┘
          │ 向量·符号索引    │           │
          └────────────────┘      ┌────▼──────────────────┐
                                  │  Worker               │
                                  │  文档解析 / 代码 AST   │
                                  │  Embedding / 调用图    │
                                  │  增量同步 / 智能体执行  │
                                  └────┬──────────────────┘
                                       │
                    ┌──────────────────▼─────────────────┐
                    │ 连接器：GitHub · Jira · 飞书 · Slack │
                    │ 对象存储 · LLM API                  │
                    └────────────────────────────────────┘
```

**只有一个数据库。** 向量用 pgvector 存在 Postgres 里，不引入独立向量库——
权限过滤和相似度排序在同一条 SQL 里完成，过滤下沉到数据库层，不可能"忘记"加它。

**可自部署。** 企业内部资料常常不允许放外部服务商，这对企业知识库是硬要求而非选项。
Docker Compose 让答案是"能装在你们机房"。于是有两种交付：SaaS（你运营）和私有部署。

## 阶段路线

阶段之间是**依赖关系**，不是偏好排序。每一阶段结束时系统必须是能用的、能演示的。

天数是**给零基础学习者的粗估**，不是承诺。

### 阶段 A：Web 客户端地基（Day 1-15）
> 状态：Day 9 完成

原计划 Day 1-15 内容不变。**目标改写为：建成多端客户端中的第一个。**

Day 11-15 的 Next.js 不能跳——它是唯一一次系统学前端工程结构的机会，
而 React Native 的组件模型和 Hooks 与 React 通用。先学扎实，将来做 App 是省力的。

### 阶段 B：后端与数据地基（约 25 天）

原 Day 16-20 扩到约 25 天，因为要多做三件"事后补要重写"的事：

1. **鉴权双模式**：Cookie（Web）+ Bearer（原生客户端）。见 `apps/api/README.md`。
2. **`resources` 通用表**：`source_type` / `external_id` / `acl_principals` 等。
3. **审计日志带 `actor_type` + `on_behalf_of`**：为智能体预留。
   **审计数据不会追溯生成**，晚一天永久少一天。

出口标准：前后端真实登录打通；用户 A 读不到用户 B 的资源；组织 X 读不到组织 Y 的；
可从空库一键迁移和回滚。

### 阶段 C：RAG 垂直链路（约 30 天）

原 Day 21-27。文档上传 → 解析 → 切分 → Embedding → 混合检索 → 带引用生成。

出口标准：20 个问题 Recall@5 ≥ 85%；跨用户与跨组织检索零泄漏；
每个事实型回答附可点击来源；无证据时明确拒答；有评估基线报告（含 P50/P95 与单次成本）。

**这是产品的最小可用形态。** 到这里为止，它是一个能用的、有引用溯源的企业文档问答。

### 阶段 D：部署与工程化（约 20 天）

原 Day 28-32。容器化、Linux 部署、HTTPS、CI/CD、可观测性、安全与压测。

**位置刻意排在代码感知之前**：没被真正部署过的系统不知道自己哪里会坏。
先让阶段 C 的东西以生产形态跑起来、被真人用过，再加新支柱。
（"生产形态"指容器化 + HTTPS + 备份 + 可观测，不等于必须有公网域名——
域名是客户的事，见 roadmap 里的交付形态一节。）

出口标准：一条命令在全新环境启动；**HTTPS 下跑通完整流程**（本地 mkcert 也算，
要验的是 Cookie/CORS 行为正确而非有公网域名）；重启自动恢复；备份**恢复**演练做过一次；
CI 能阻断失败提交；能从一次失败请求定位到检索与模型调用；日志不含令牌与私有文档全文。

### 阶段 E：代码感知（约 45 天）★ 差异化从这里开始

前置：阶段 C（检索链路）+ 阶段 D（上线过）。

- GitHub 连接器：仓库、PR、issue、review 讨论、commit 历史
- 代码感知切分：按 AST 切函数与类，而不是按字符数——切在函数中间的 chunk 检索质量极差
- 符号索引：`getUserById` 定义在哪、被谁引用
- 调用图与依赖图构建
- **推导式架构图**：节点可点开看文件，边可追到 import 那一行
- **影响面分析**：改这个函数会影响到哪（CLI 可在 CI 里跑，输出到 PR 评论）
- **变更归因**："这段代码为什么是这样"——串联代码 + PR 讨论 + 设计文档 + 事故复盘

出口标准：对一个真实的中等规模仓库，回答"这段代码为什么这样"能给出跨源引用；
架构图的每个节点和边都可追溯到源码位置；影响面分析的召回率有可测数字。

### 阶段 F：智能体治理（约 40 天）

前置：阶段 B（组织/ACL/审计）+ 阶段 C（检索）。

- 智能体注册表：定义、工具集、可访问的数据范围
- **权限继承**：智能体以用户身份行动，绝不越权
- 运行审计：每一次执行做了什么、代表谁、读了哪些资源
- 成本账本：token 用量按组织/部门/智能体归集，可设预算与硬上限
- 提示注入防线：不可信文档内容与指令的隔离
- 工具调用框架：让智能体能调用检索、代码分析、外部 API

出口标准：智能体读不到它所代表的用户读不到的任何东西（红队测试）；
任一次智能体运行可完整回放；超预算会被拦住而不是产生账单。

### 阶段 G：多端客户端（约 50 天）

前置：阶段 B（鉴权双模式）+ 阶段 D（有稳定的线上 API）。

顺序刻意如此：

```
PWA（最便宜：manifest + Service Worker，可安装、能离线打开）
  → 收集真实使用数据，再决定要不要投原生
  → IDE 插件（程序员向的最高价值界面，且技术上最简单——它就是个 API 客户端）
  → Tauri 桌面端（可直接复用 Next.js 前端）
  → React Native 手机端（投入最大，放最后）
```

**先 PWA 的理由**：企业内部工具的真相是员工多数在电脑前工作，
手机端使用率可能低到不值得做原生。用零成本的一步收数据，比直接投三个月更稳。

### 阶段 H：企业统一搜索（约 60 天）

原 Phase 2 内容。多连接器（飞书/Slack/Jira/Confluence）、增量同步与删除传播、
跨源统一排序、权限正确性红队 200 条断言、实体图谱、点击反馈 rerank、百万级压测。

放在最后的理由：**连接器是工程量而非难度**（每个 800-1500 行、1-2 周，
含 OAuth/分页/增量游标/限流/删除事件）。它扩大覆盖面，但不创造新的产品能力。
在只有一个数据源时把支柱二和三做扎实，比在五个数据源上做出五个半成品更有价值。

## 优先级判据

**瓶颈不是想法，是取舍。** 上面每一阶段都是几十天，而执行者是一个人。

判据：**一个能回答"这段代码为什么是这样"并且每句话都能点开看出处的工具，
即使只支持 GitHub 一个数据源，也比十个半成品功能有价值。**

所以路线的形状是：**先把一条链路做到能用，再加下一条。**
每个阶段出口都要求"能演示、能被真人用"，不接受"框架搭好了但跑不通"。

## 不做的清单（写下来防止反复讨论）

- IM / 语音会议 / 日历 / 在线文档编辑器 —— 理由见开头
- 独立向量数据库 —— pgvector 让权限过滤下沉到 SQL
- 自研 LLM —— 用 API，把精力放在检索质量和治理上
- LLM 直接画架构图 —— 必须从真实代码结构推导
- 手写代码练习 —— 学习方式是完整实现 + 逐行剖析 + 问答检验
