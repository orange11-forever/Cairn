# 第一部分：八个场景

## 场景一：新人第一天，看不懂一段代码（E）

在 VS Code 里打开 `billing/calculator.py`，看到一段奇怪的判断：

```python
if user.plan == "legacy_pro" and created_at < CUTOFF:
    discount = 0.15   # 为什么是 0.15？为什么有这个分支？
```

选中这三行，右键 → **"为什么这样写"**：

```
┌─ Cairn ─────────────────────────────────────────┐
│                                                     │
│  这个分支是 2024-03 为了兼容老客户加的。             │
│  0.15 来自当时和销售定的过渡方案：legacy_pro         │
│  用户保留原折扣直到合同到期。                        │
│                                                     │
│  📎 来源                                            │
│  ① PR #1823 的讨论 —— 张伟：                        │
│     "直接改价会违反已签合同，先留个分支"             │
│  ② 设计文档《计费迁移方案》第 3 节                   │
│  ③ commit a3f9c2 "hotfix: 老客户折扣回退"           │
│  ④ 事故复盘 2024-03-14 —— 上一版漏了这个分支，       │
│     导致 40 个客户被多收费                          │
│                                                     │
│  ⚠️ 相关：CUTOFF 常量在 config.py:88，              │
│     最后一次修改是 6 个月前                          │
└─────────────────────────────────────────────────────┘
```

每一条都能点开跳到原文。这个答案原本要花他半天，或者去打断一个待了五年的同事。

**这是整个产品的核心场景。** 其他功能都是为了让这一刻成立。

```
$ cairn impact calculate_discount

影响面分析
──────────────────────────────────────────

  billing/invoice.py:142
  billing/preview.py:67
  api/v1/orders.py:203
  jobs/monthly_billing.py:31      ⚠️ 定时任务，改错要等月底才发现

间接影响 (11 处，2 层内)
  → 展开查看

  tests/test_billing.py            5 个
  tests/test_invoice_e2e.py        2 个

⚠️ 高风险提示
  monthly_billing.py 没有单测覆盖这条路径
  这个函数半年内改过 4 次，其中 1 次引发事故
```

这个分析**可以直接跑在 CI 里**，结果自动贴到 PR 评论下面——
不需要谁记得主动打开工具。**被动触达比主动使用的留存高一个量级。**

## 场景三：这个 PR 让架构变成了什么样（E）

**这是图相关功能里价值最高的形态**，不是静态的架构图。

提了一个 PR，CI 自动在评论里贴出：

```
┌─ Cairn · 架构影响 ──────────────────────────────────┐
│                                                     │
│  + billing/calculator.py → external/tax_api.py      │
│    【新增依赖】                                      │
│  - billing/invoice.py    → utils/legacy_fmt.py      │
│    【移除依赖】                                      │
│                                                     │
│  ⚠️ 新增了一条 billing → external 的依赖。          │
│     这个方向此前不存在——billing 一直是不出网的。     │
│                                                     │
│  影响面：4 个直接调用方，7 个测试会失效              │
│  [查看完整图]                                        │
└─────────────────────────────────────────────────────┘
```

为什么它比"看架构图"有用：

**一、出现在有人做决定的时刻。** 审查者本来就在判断"这个改动可以吗"，
而"新增了一条跨层依赖"很难靠读 diff 发现——它藏在一行 import 里。

**二、被动触达。** 自动贴评论，不需要谁记得打开工具。

**三、架构腐化是渐进的。** 没人会一次性把架构搞坏，都是每个 PR 加一条
"就这一次"的依赖，两年后没人认得出原来的设计。这是唯一能在每次改动时
看见这个过程的东西。

## 场景四：一张图回答一个问题（E）

```
$ cairn deps billing/
```

```
     ┌─────────────┐
     │  api/v1     │  ← 点开：3 个文件，最近改动 2 天前
     └──────┬──────┘
            │ import（实线 = 静态确定）
     ┌──────▼──────────────────┐
     │  billing/               │  🔥 变更热点
     │  ├─ calculator.py       │     "近 3 个月改了 12 次，
     │  ├─ invoice.py          │      多数与 legacy_pro 分支有关"
     │  └─ preview.py          │
     └──────┬──────────┄┄┄┄┄┄┄─┘
            │          ┄ 虚线 = 类型推断
     ┌──────▼──────┐    ┌──────────────┐
     │  models/    │    │  jobs/       │
     │  User       │◄╌?╌│ monthly_     │  ╌?╌ = 可能存在，
     │  Plan       │    │ billing      │       无法静态确认
     └─────────────┘    └──────────────┘
```

**三个关键设计**：

**一、不做"全貌图"。** 一个真实项目有 300 个文件、2000 条边，全画出来是毛线球，
**比不画更糟**——它给人"看到了全貌"的错觉。所以每张图回答一个具体问题：
"billing 依赖什么"、"改这个函数波及谁"、"这个请求走过哪些层"。

市面上大部分"自动生成架构图"的工具就死在这里。

**二、边的置信度必须区分**（看上面三种线型）：

| 来源 | 确定性 |
|---|---|
| `import` 语句、直接调用 | 实线，**确定**，可点到具体那一行 |
| `obj.method()` | 虚线，**推断**（动态语言里类型要靠推断） |
| 反射、装饰器、事件队列 | 问号，**可能漏** |

把一条猜出来的边画成实线，和让 LLM 编一个答案是同一类错误。
诚实地说"这里我不确定"比假装全知更可信。

**三、图不是 AI 画的。** 从真实 `import` 和调用关系推导，点节点跳到文件，
点边看到那一行。AI 只负责给"变更热点"写那句人话总结。

LLM 画的架构图会自信地错，而**图比文字更容易让人相信**，所以错得更危险。

## 场景五：上传一份文档（A 前端已做 / C 接真解析）

```
┌─ 上传文档 ──────────────────────────────────┐
│  拖拽文件到此处                              │
│  支持 .pdf .md .txt .docx，单个 ≤ 10MB      │
├─────────────────────────────────────────────┤
│  ✓ 值班流程 v3.pdf        2.1 MB   已就绪   │
│  ⟳ 架构设计.docx          890 KB   处理中… │
│  ✗ 财务报表.xlsx          1.2 MB            │
│      不支持 .xlsx 格式，请上传 .pdf         │
│  ⚠ 扫描件.pdf             5.4 MB   失败    │
│      第 3-8 页是扫描图，需要 OCR            │
│      [启用 OCR 重试]  [仅索引可读页面]      │
└─────────────────────────────────────────────┘
```

三个细节是刻意的：

- **每个文件的错误显示在它自己那一行**，不是顶部一句"部分文件有问题"让人猜
- 失败给的是**真实原因和下一步动作**，不是"处理失败"四个字
- 状态是「已就绪」而不是「上传成功」——文档要解析完才能被检索到，
  说"成功"会让人立刻去提问然后失望

```
│                                                 │

│  ② 事故响应 SOP，升级矩阵                       │
└─────────────────────────────────────────────────┘
```

换一个知识库里没有的问题：

```
┌─────────────────────────────────────────────────┐
│  Q: 竞品的定价策略是什么？                      │
├─────────────────────────────────────────────────┤
│  ⚠️ 知识库里没有找到相关依据。                  │
│                                                 │
│  我不猜。可能的原因：                           │
│  · 相关文档还没上传                             │
│  · 你没有访问那些文档的权限                     │
│                                                 │
│  [搜索相似内容]  [申请权限]                     │
└─────────────────────────────────────────────────┘
```

**这是功能，不是缺陷。** 企业里一个编造的答案比没有答案代价大得多——
用户会拿它去做决定。

## 场景七：不用打开这个软件也能用它（G）

在飞书群里：

```
张伟      @Cairn 我们的日志保留多久？

Cairn 生产环境 30 天，审计日志 3 年。
          📎 ① 运维手册 2.4  ② 合规要求清单
          （张伟你可见的 2 份文档）
```

**用户不改变任何习惯。** 这比"请大家搬到我的平台"好一个量级——
它作为数据源吃进飞书，同时作为机器人在飞书里交付答案。

注意最后那行括号：**答案只用提问者有权看到的文档**。同一个问题，
不同人问可能得到不同答案，这是正确行为。

## 场景八：智能体，但看得住（F）

创建一个自动 PR 审查的智能体：

```
┌─ 新建智能体 ────────────────────────────────┐
│  名称    PR 审查助手                        │
│  触发    ● 新 PR 时  ○ 定时  ○ 手动        │
│  工具    ☑ 代码检索  ☑ 影响面分析          │
│          ☑ 读设计文档  ☐ 外部 API          │
│                                             │
│  权限    ⚠️ 以【提交 PR 的那个人】身份运行  │
│          读不到那个人读不到的东西            │
│                                             │
│  预算    每月 200,000 tokens                │
│          超出后 ● 停止  ○ 通知管理员        │
└─────────────────────────────────────────────┘
```

管理员能看到它干了什么：

```
运行记录 · PR 审查助手
──────────────────────────────────────────────
今天 14:32  代表 张伟   PR #2041
            读取 4 个资源 · 8,200 tokens
            [查看完整对话]

今天 11:05  代表 李娜   PR #2038
            读取 7 个资源 · 12,400 tokens

本月用量  ████████░░  164k / 200k
```

**"代表谁运行"这一栏是整个设计的关键。** 没有它，智能体就是一个越权通道——
实习生的智能体读到了 CEO 的文档。

## 三、代码感知（★ 差异化）

| 功能 | 说明 | 阶段 |
|---|---|---|
| **「这段代码为什么是这样」** | 串联 commit + PR 讨论 + 设计文档 + 事故复盘 | E |

| **★ 图的 diff（PR 架构影响）** | 这个 PR 新增/移除了哪些依赖，自动贴 PR 评论。**优先级最高的图形态** | E |
| 依赖图 | 从真实 `import` 推导，每条边可点到那一行。**可靠** | E |
| 调用图 | 动态语言里**必然近似**，边要标注置信度 | E |

| 变更热点 | 哪些文件最近改得频繁，并总结为什么 | E |
| 新人上手路径 | 给一个仓库，生成"按这个顺序读这几个文件" | E |
| 代码 ↔ 文档双向链接 | 这份设计文档对应哪些代码，反之亦然 | E |

**图的四条设计决定**（详见 [`roadmap.md`](roadmap.md) 阶段 E）：
一张图回答一个问题（不做全貌图）· 边必须标注置信度 ·
先做依赖图后做调用图 · 图的 diff 优先级最高。

渲染分两条路：PR 评论用 **Mermaid**（GitHub 原生渲染，零成本嵌入），
交互式查看自渲染 SVG + `elkjs` 布局。解析用 **tree-sitter**（一套 API 支持几十种语言）。

# 最小可用产品（MVP）

上面是完整清单。**能先跑起来、能被真人用**的是这五条（阶段 A→B→C→D）：

```
① 登录、组织、权限隔离
② 上传文档 → 看到处理状态 → 失败能重试
③ 提问 → 带可点击引用的答案 → 无依据就拒答   ← 产品的全部意义
④ 对话历史
⑤ 部署上线
```

第 ③ 条是核心，其余四条是让它能被真实使用的最小配套。

**代码感知（场景一二三）和智能体（场景七）是在这个地基上加的，不是并行做的**——
它们都依赖"检索能返回正确且带权限过滤的结果"，而那个前提要到阶段 C 结束才成立。
